# 小型 smoke：CPU 与 Metal 实测（2026-09-18）

**小训练确实可能 CPU 更快。** 本机上，32 条极小 smoke 和较小模型的
4,096 条 smoke 都由 CPU 获胜；正式 16 层／192 通道模型跑 4,096 条时，
Metal 更快。移除 CPU 训练入口是维护取舍，不是所有小训练都能提速的结论。

## 结果

下表为三个独立进程运行的**中位数总耗时**。CPU 列取 1、5 线程中中位数
更快的一组；两种线程设置均重复了三次。GPU 使用 1 个 host CPU 线程。

| 模型、训练规模 | 训练批次 | CPU 总耗时 | Metal 总耗时 | 结果 |
| --- | ---: | ---: | ---: | --- |
| 16 层／192 通道，32 条，batch 上限 4 | 10 | 1.67 秒（1 线程） | 2.48 秒 | Metal 多用约 49% 时间 |
| 16 层／192 通道，4,096 条，batch 上限 128 | 36 | 4.87 秒（5 线程） | 3.57 秒 | Metal 少用约 27% 时间 |
| 8 层／64 通道，4,096 条，batch 上限 128 | 36 | 2.34 秒（5 线程） | 2.93 秒 | Metal 多用约 26% 时间 |

训练循环本身的中位数（包含首批编译和输入传输，不预热）：

| 同上三组 | CPU 1 线程 | CPU 5 线程 | Metal |
| --- | ---: | ---: | ---: |
| 正式模型，32 条 | 0.142 秒 | 0.202 秒 | 0.559 秒 |
| 正式模型，4,096 条 | 4.325 秒 | 2.909 秒 | 1.279 秒 |
| 小模型，4,096 条 | 0.647 秒 | 0.457 秒 | 0.767 秒 |

正式模型的 4,096 条 smoke，训练循环约快 2.28 倍，但总流程只快约 1.37 倍。
导入依赖、加载检查点、初始化、验证和保存等固定开销会稀释计算加速。
小模型／小批次计算量不足时，本次连训练循环也由 CPU 更快。

## 方法与适用范围

- Apple M5 Pro、24 GiB 内存、PyTorch 2.8.0，全部 FP32。
- 三种场景 × CPU 1 线程／CPU 5 线程／Metal × 三次重复，共 27 次。
  每次使用全新 Python 进程，轮换设备顺序；不预热模型，也不清空系统文件缓存。
- CPU 使用冻结历史源码中的三次矩阵乘法实现，Metal 使用等价原生 Conv1d。
  测速代码位于忽略的实验目录，没有重新打开正式 CPU 训练入口。
- 每组设备使用完全相同的初始权重、AdamW 状态、输入、标签、批次顺序、
  域和位置权重、学习率 0.0003、weight decay 0.0001、梯度裁剪 1。
  loss 同除以正式日志给出的 0.982851；这个六位小数常数只用于本次对照。
- 正式模型两组复制当时的训练检查点；小模型使用固定随机种子和新 AdamW。
  三组均保留 8,192 字词表。不同组间的准确率不作比较。
- 固定数据来自本地 v7 Wikipedia、合成和网页训练分片。小基准只取 8–96
  字输入；4,096 条的平均长度约 28 字。它不代表极长句的性能。
  极小 smoke 使用 16 条 validation、16 条 test；其余每组各 128 条。
  这些是测速用的固定子集，正式完整验证／测试没有变化。
- 总耗时从启动子进程到退出：包括导入、准备输入和模型、训练一轮、验证／测试、
  CPU 可读训练检查点及 safetensors 保存、额外预测一致性核查和退出。
  GPU 每步保留 `loss.item()` 同步。实验更新和生成权重均不用于正式训练。
- 27 次的损失均有限。各组 CPU/Metal 在其固定测试输入上的预测全部一致；
  与 CPU 1 线程比较的逐步 loss 最大差分别为 0.000416、0.0000238、0.00000763。
  小子集一致不能保证长期轨迹或全量准确率一致。

开始对照前发现正式 Metal 任务已因内存上限退出，因此实际 86.36 秒的测试
期间没有并行训练争用 CPU/GPU，也没有对正式任务发送暂停信号。最初计划的
挂起／恢复逻辑未触发。该故障与处理结果见下面的运行记录。

本地复现材料：`training/artifacts/small-smoke-speed-20260918/` 中的
`compare.py`、`timed_train_smoke.py`、三个固定 `.pt`、`preparation.json`、
`trials.json`、`summary.json` 和每次日志。结果 JSON 保留全部计时和预测。

## 对照时发现的正式任务内存故障

正式任务于 11:05 CST 因 MPS OOM 退出。错误报告分配上限约 4.44 GiB，
allocator 约 1.34 GiB，其他 driver allocations 约 3.08 GiB。
最近的完整检查点为 epoch 1、shard 352（从零开始）、36,446,454 条；
检查点之后未保存的少量批次需要重算。

原设置只把硬上限降至推荐内存的 0.25，却没有同步设置较低的软回收水位。
[PyTorch 2.8 文档](https://docs.pytorch.org/docs/2.8/mps_environment_variables.html)
规定软水位用于触发缓存回收和更频繁的提交。
此外，[MPSGraphCache 源码](https://github.com/pytorch/pytorch/blob/v2.8.0/aten/src/ATen/native/mps/OperationUtils.h)
显示它在进程内保存图缓存；[empty_cache](https://docs.pytorch.org/docs/2.8/generated/torch.mps.empty_cache.html)
释放的是空闲 allocator 缓存。变长输入的图缓存因此是需要防范的来源，
但没有据此断言它解释了全部“其他分配”。

修正运行机制：硬上限 0.4（本机约 7.1 GiB），软水位 0.24；释放已完成
batch 的图引用，每分片清理空闲缓存。安全批次结束后，若 driver 使用量
清理后仍达到硬上限的 60%，先保存完整下一批次位置，再以退出码 75 请求
协调器启动新进程，从原模型／AdamW／数据顺序继续，释放进程级图缓存。
保存后的权重归一化常数与配置、数据身份绑定，工作进程恢复时可复用。
该处理没有减小 batch、截断输入或跳过任何样本。

检查通过：15 项 Python 测试、223 项 Node 测试，包括模拟内存压力退出 75
后下一批次精确恢复，以及完整 fixture 验证／测试和浏览器导出。
这验证恢复机制，不是一次完整长训练的稳定性证明。

实际恢复后已重新保存 shard 356、36,918,622 条处的检查点，较恢复起点
推进 472,168 条，越过此前 OOM 的分片。检查点中的数据身份、训练配置和
词表保持一致，模型权重及 AdamW 状态均为有限数值；正式任务继续运行。
核查记录保存在正式任务目录的 `mps-memory-recovery-verification.json`。
