# 训练提速研究：2026-09-18

优先考虑 **PyTorch MPS GPU + 等价原生 Conv1d**。在同一份真实数据、权重、
AdamW 状态和批次顺序下，小基准的稳定吞吐约为 CPU 的 **5.2 倍**。
CPU 合并矩阵乘法约提高 **34%**；单纯增加 CPU 线程没有明显收益。

研究阶段使用独立实验，正式 v7 训练当时继续按原 CPU 配置运行。没有修改它的代码快照、
检查点、数据、训练批次或评估标准；后续正式接入记录见下节。基准与正式训练并行，会竞争部分机器资源，
因此表中数字不是停掉所有其他任务后的独占性能，也不能直接等同于整轮加速比。

## 环境与控制变量

- Apple M5 Pro，18 核 CPU，24 GiB 统一内存，macOS 26.6.2。
- 本地 PyTorch 2.8.0，MPS 可用；所有对比使用 FP32。
- 16 层卷积、192 通道、8,192 字符词表，结构和参数形状保持一致。
- 初始化复制正式训练 epoch 1、已处理 30,219,133 条样本的检查点。
- 来自 Wikipedia、合成和网页训练分片的固定数据；每次 28 批、5,441 条。
  使用原有分桶和 512 条／8,192 padded tokens 的批次限制，形状包括 6×309、
  256×32、128×64、64×126 等。
- 所有实现从同一模型和优化器状态开始，保留梯度裁剪、域与位置样本权重、
  每步 `loss.item()`。损失归一化常数取正式日志的 0.982851（六位小数）。
- GPU 计时包含输入设备传输，并同步 GPU；禁用 CPU fallback 和 fast math。
  这是 PyTorch 官方要求的设备迁移方式及同步 API：
  [MPS 后端](https://docs.pytorch.org/docs/2.8/notes/mps.html)、
  [同步](https://docs.pytorch.org/docs/2.8/generated/torch.mps.synchronize.html)、
  [环境变量](https://docs.pytorch.org/docs/2.8/mps_environment_variables.html)。

## 吞吐结果

每组先预热四个批次，再计时两遍。第二遍用于观察这些形状缓存后的吞吐；
第一遍仍包含未预热形状的初始化成本。CPU 基准和推荐 GPU 方案各另重复一次。

| 设备与实现 | 每秒样本，第二遍 | 相对 CPU 基准 | 判断 |
| --- | ---: | ---: | --- |
| CPU，现有实现，5 线程 | 1,036–1,049 | 1.00 | 基准 |
| CPU，现有实现，1 线程 | 908 | 0.87 | 更慢 |
| CPU，现有实现，3 线程 | 1,003 | 0.96 | 无收益 |
| CPU，现有实现，8 线程 | 1,036 | 0.99 | 无收益 |
| CPU，三次矩阵乘法合并为一次，5 线程 | 1,407 | 1.34 | 可作为 CPU 优化 |
| CPU，原生 Conv1d，5 线程 | 171 | 0.16 | 不适合本机 CPU |
| MPS GPU，原生 Conv1d | 5,436–5,437 | 5.19 | 优先方案 |
| MPS GPU，合并矩阵乘法 | 5,289 | 5.04 | 可行备选 |

相对值以四次 CPU 计时的平均 1,048 条／秒计算。GPU 原生卷积第一遍为
4,459–4,563 条／秒。额外的 112 步连续训练对比为 CPU 19.69 秒、GPU 4.49 秒，
CPU 在该正确性复核中使用 3 线程，因此不把它混入上表的 5 线程速度比。

正式训练之前实测约 1,200–1,300 条／秒，比并行 CPU 基准更快。因此，
对完整一轮更保守的初步预期是 **约 3–4 倍加速**：1.4627 亿条样本的训练部分
可能从约 30–33 小时降到 **8–10 小时**。这只是外推，尚无完整 GPU epoch；
数据准备时间不会因此同步缩短，实际吞吐还受数据读取、变长形状与其他应用影响。

## 正确性检查及直接迁移问题

**不能直接把现有 `ThreeTapConv1d` 原样移到 MPS。** 本机环境中，该路径的
非连续权重切片线性运算出现严重数值不一致：损失可达数万，预测与 CPU 不同。
即使吞吐看起来很高，这组结果也不可用。`PYTORCH_MPS_PREFER_METAL=1` 没有解决。
对每个权重切片调用 `.contiguous()` 后，数值检查恢复正常；原生卷积和
合并矩阵乘法也正常。这定位到当前环境下的非连续切片计算路径，尚未证明
该现象在其他 PyTorch 版本或硬件上也存在。

推荐的原生卷积只改变执行方式，仍使用同名、同形状的 `[out, in, 3]` 权重，
padding、残差、LayerNorm、GELU、掩码和 gap head 都保持原样。

检查结果：

- 六组批次、共 46 条样本的初始前向与反向：预测全部一致；最大损失绝对差
  `8.20e-7`，最大梯度相对 L2 差 `1.15e-5`，最大 logit 绝对差 `5.19e-4`。
- 连续 112 步（21,764 条次）后，逐步损失最大绝对差 `1.74e-5`；
  随后在固定 1,024 条验证输入上的预测一致率为 **100%**。
  这只是后端数值一致性检查，不能代替正式的 252 万条完整 validation，
  也不能证明长期训练轨迹逐位相同或最终质量相同。
- 参数不是逐位相同，整体相对 L2 差约 `1.05e-5`。最大绝对差 `0.01329`
  来自 `boundary_output.bias`；它对所有有效 gap 加同一个常数，softmax 对
  这种平移不敏感。其次为末层卷积权重，最大差约 `5.37e-4`。
- 长度 2、3、8,192 和语料实际最大长度 17,911 的**合成 token 序列**压力测试
  均完成前向／反向，损失和梯度有限；最大梯度相对 L2 差约 `4.27e-5`。
  这些用来覆盖形状上限，不是对真实最长文本的语义评估。

## 其他瓶颈与接入优先级

CPU 训练步骤计时中，前向及损失占 37.7%，反向占 58.4%，优化器占 3.0%，
梯度裁剪占 0.7%。这里的分母仅为测量到的训练步骤，不包括读取分片和评估。
算子剖析中 `mm/addmm` 占约 54% 自身 CPU 时间，复制操作占约 11%。
计算部分是首先值得优化的地方。

建议按以下顺序接入：

1. 增加显式 CPU／MPS 设备配置；MPS 使用等价原生卷积。迁移输入及优化器状态，
   修正评估中的 `.numpy()` 为先搬回 CPU，确保保存、恢复、最终浏览器导出保持兼容。
   先在独立候选目录验证完整训练、保存、恢复和评估路径，再用于正式长训练。
2. 为 `combined_weight_mean` 保存与数据身份绑定的缓存。当前每次启动／恢复
   都会重扫 1.46 亿条 JSONL，只为重算这个标量；这能减少恢复等待，
   不能把它算成稳定训练吞吐的数倍提升。
3. 精简完整验证集的内存表示，缓存字符 ID，减少重复 JSON 解析和 Python 对象。
   不减少验证或测试样本。GPU 接入后再测这部分开销是否成为主要限制。
4. 保留 CPU 合并矩阵乘法作为回退方案。当前没有证据支持增加到 8 个 CPU 线程。

本轮没有改变 batch size、降低精度、截断长句、减少验证集或改动损失函数来换速度。
也没有实测 MLX、其他 PyTorch 版本、远程 GPU 或混合精度，因此不为它们给出速度承诺。

## 正式接入：2026-09-18

用户确认后，接入 `train_sharded.py --device mps`。共享模型仅在 MPS 上走
原生 Conv1d，CPU 仍走已验证的原实现；输入、评估和预测支持设备搬移。
最新权重、AdamW 一二阶矩和最佳模型快照均保存为 CPU 张量，检查点可在两种
设备间恢复。执行设备作为独立元数据记录，不放入必须严格相同的训练配置。

5 项新增测试通过，包括带 padding 的 16 层前后向一致性、评估和预测、
优化器下一步恢复一致性，以及 192 通道／16 层模型的完整小样本流程：
CPU 收到 SIGTERM 保存 → MPS 续训 → 完整 fixture validation/test →
浏览器导出推理对齐。另有 5 项数据准备测试和 224 项 Node 测试通过。
这些检查验证程序路径，不是新的正式准确率结果。

正式 CPU 任务于 10:38 CST 保存并退出：epoch 1，已见 32,665,991 条，
下一位置为 shard 314 / batch 396（均为从零开始的索引），AdamW 已更新
168,904 步。保留原始 `run.json` 和 `source/`，另冻结训练代码到
`training-runtimes/20260918T023858016039Z/source/`，并在同目录上层保存
`before-migration.pt`。迁移没有重新初始化模型或优化器。

`training-runtime.json` 固定设备与源码哈希；协调器采用 MPS、FP32、1 个 CPU
线程和 0.25 GPU 内存配额。后续普通
`npm run model:retrain-surface -- --resume` 会自动采用该训练快照。
完整训练样本 146,266,210 条、验证 2,522,347 条、测试 2,569,996 条均不变。
数据统计启动扫描和验证集 Python 对象加载的优化留待后续处理。

恢复日志确认下一步为 `epoch=1 shard=314 next_batch=396`。首个正式 MPS
检查点已推进到 32,878,025 条、shard 316、AdamW 第 169,980 步；全部模型和
优化器张量均为有限值，落盘在 CPU，配置、数据身份和词表与迁移前完全一致。
从恢复点到该检查点推进 212,034 条，用时 70.20 秒，约 **3,021 条／秒**，
包含分片读取、垃圾回收等训练循环开销，不含启动阶段约 3 分钟的数据加载。
这低于独立小基准 5,436 条／秒；对比此前 CPU 全流程约 1,200–1,300 条／秒，
初步约快 2.3–2.5 倍。两段数据不同且 GPU 观察时间短，不能当作最终整轮加速比。
按这一初始吞吐外推，剩余训练约 10.4 小时，另需完整验证和测试；之前
8–10 小时整轮的估算应以此次实测继续修正。
